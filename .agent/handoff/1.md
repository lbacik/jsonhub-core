## Known issues

- **Sorting judgment call — needs human eyes.** Implemented TRUE UTF-16
  code-unit order per RFC 8785 §3.2.3 (verified via rfc-editor.org):
  key U+1F600 (units D83D DE00) sorts BEFORE key U+E000 (unit E000).
  The brief states the rule 3x ("sorted by UTF-16 code units", PRD §7.1
  agrees, `ext-mbstring` hint implies UTF-16 conversion) but its example
  sentence says the opposite (E000 before 😀 — that is the code-point /
  UTF-8-byte outcome, contradicting its own "not UTF-8 bytes").
  `CanonicalJsonSpec::it_sorts_members_by_utf16_code_units` pins 😀-first
  with an explanatory comment. If E000-first is wanted instead, it is a
  small change (compare decoded code points / UTF-8 bytes instead of the
  UTF-16BE sort key in `Reader`) plus a spec update.
- **Legacy number normalization keeps the input shape** (strips redundant
  zeros, lowercases `e`, drops `+`/zero exponents) so the brief's
  "preserved exactly" cases are byte-identical (`9007199254740993`,
  `1e400`, `0.10000000000000000001`). Cross-shape uniqueness (e.g.
  `1500` vs `1.5e3`, both strict-passing anyway) is therefore not forced
  for legacy-exception numbers.
- **`invalid_json` pointer format** (brief: "enclosing value, plus a byte
  offset"): `<pointer>#<offset>`, e.g. `/a#6`, `#0`. Pinned in specs.
- **`1e21` / max-double literals are strict-rejected** (`unsafe_integer`:
  integer-valued, |v| > 2^53-1 — same as the brief's `1e16` example), so
  their JCS serializations (`1e+21`, `1.7976931348623157e+308`) are covered
  at the `Decimal::esToString` unit level in `DecimalSpec`, not via
  `strict()`. Verified these outputs match RFC 8785 Appendix B.
